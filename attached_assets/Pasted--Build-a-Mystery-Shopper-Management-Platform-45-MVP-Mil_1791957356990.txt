# Build a Mystery Shopper Management Platform — 45% MVP Milestone

Act as a senior full-stack developer. Build a professional, functional MVP of a **Mystery Shopper Management Platform** for a company that helps brands evaluate the quality of their retail stores.

## 1. Main Objective

Build the first approximately 45% of the complete product. Prioritize working functionality, database persistence, clean architecture, and a professional interface. Do not build every feature at once.

The application must be a real working application, not just a static UI prototype. Do not claim that a feature works unless it has actually been implemented and tested.

## 2. Technology Stack

First inspect the available Replit environment and choose the simplest supported full-stack stack.

Preferred:
- React with TypeScript for the frontend.
- Tailwind CSS for styling.
- A persistent PostgreSQL database if available.
- A secure backend/API for database operations.
- Use environment variables for credentials and secrets.

If a preferred technology is unavailable, choose a compatible alternative and explain the choice. Do not introduce unnecessary services or paid dependencies.

## 3. Professional UI Requirements

Create a polished enterprise SaaS dashboard with:
- A clean white and light-grey interface.
- Dark navy text and a restrained blue accent.
- A collapsible sidebar and a top navigation bar.
- Responsive layouts for desktop, tablet, and mobile.
- Consistent spacing, typography, cards, tables, badges, forms, and modals.
- Loading states, empty states, validation messages, and error handling.

Sidebar navigation:
1. Dashboard
2. Stores
3. Mystery Shoppers
4. Verification
5. Tasks
6. Questionnaires
7. Reports
8. Settings

Do not use excessive gradients, emojis, or unnecessary animations.

## 4. User Roles

Prepare the application architecture for these roles:
- Admin: manages the platform.
- Mystery Shopper: receives assigned visits and submits reports.
- Reviewer: checks submissions and approves or rejects them.
- Regional Executive: views store performance and scorecards.

For this initial milestone, prioritize the Admin workflow. Do not create fake security by simply hiding buttons. Enforce permissions on the backend for any implemented authentication and role-based access.

## 5. Implement These Features First

### A. Dashboard
Create a functional admin dashboard displaying:
- Total stores.
- Total registered shoppers.
- Pending shopper verifications.
- Total tasks.
- Pending and completed tasks.
- Recent tasks and activity.

All figures must come from the database, not hardcoded demo numbers. Show useful empty states when no data exists.

### B. Store Management
Implement:
- View stores in a searchable, filterable table.
- Add a store.
- Edit store details.
- View store details.
- Delete a store with confirmation.

Store fields:
- Store name.
- Store code.
- Brand name.
- Region.
- City.
- Address.
- Contact person.
- Contact phone.
- Status.

Validate required fields and prevent duplicate store codes.

### C. Mystery Shopper Management
Implement:
- View shoppers in a table.
- Add a shopper.
- Edit shopper information.
- View shopper details.
- Search and filter shoppers.
- Set verification status.

Shopper fields:
- Full name.
- Email.
- Phone.
- City.
- Experience.
- Verification status: Pending, Verified, Rejected.
- Account status: Active or Inactive.

Prevent duplicate email addresses. Use appropriate validation and do not store unnecessary sensitive personal information.

### D. Shopper Verification
Create a dedicated verification page where an admin can:
- View pending shoppers.
- Inspect their submitted profile information.
- Approve or reject a shopper.
- Record the decision and timestamp.
- Add an optional reason for rejection.

Only verified and active shoppers should be eligible for new task assignments.

### E. Task Management
Implement:
- View all tasks.
- Create a task.
- Select a store.
- Select an eligible verified shopper.
- Set the visit date and due date.
- Add visit instructions.
- Set priority and status.
- View task details.

Task statuses should include Draft, Assigned, In Progress, Submitted, Approved, Rejected, and Cancelled.

Validate dates and required fields. Save tasks persistently in the database.

### F. Questionnaire Builder
Implement a basic questionnaire management feature:
- Create a questionnaire.
- Add questions.
- Support text, single-choice, yes/no, and rating questions.
- Mark questions as required.
- Edit and view questionnaires.
- Activate or deactivate questionnaires.

Questionnaire fields should include title, description, status, and questions. Store questions in a structured and maintainable format.

## 6. Database Design

Create appropriate persistent database tables and relationships for:
- Users.
- Stores.
- Shopper profiles.
- Tasks.
- Questionnaires.
- Questionnaire questions.
- Verification decisions.
- Activity logs, if practical.

Use appropriate IDs, timestamps, constraints, and foreign keys. Keep the schema maintainable and avoid storing the same information unnecessarily.

If authentication is implemented, use a supported secure authentication method. Never hardcode passwords, API keys, or database credentials. Do not expose secrets in frontend code.

## 7. Important Scope Boundaries

This is the first approximately 45% milestone, not the entire finished product.

Prioritize these working flows:
1. Admin can create and manage stores.
2. Admin can register and verify shoppers.
3. Admin can create questionnaires.
4. Admin can create tasks and assign them only to eligible verified shoppers.
5. Dashboard figures update based on actual database records.

Do not spend time yet on advanced analytics, automated payments, GPS verification, native mobile apps, complex multi-tenant billing, or advanced AI features.

Prepare the architecture so that later milestones can add:
- Shopper task acceptance and visit submission.
- Photo evidence uploads.
- Reviewer approval and rejection workflow.
- Automatic scoring and store scorecards.
- Regional executive dashboards.

Do not display these future features as fully functional if they have not been implemented.

## 8. Development Process

Work in small stages:

Stage 1: Inspect the environment, set up the application, database, and core layout.

Stage 2: Implement database schema and the store management module.

Stage 3: Implement shopper management and verification.

Stage 4: Implement questionnaires and task creation/assignment.

Stage 5: Connect dashboard metrics, validate forms, and test the core workflows.

After each stage:
- Run the application.
- Fix build errors and runtime errors.
- Test the implemented functionality.
- Verify that data persists after refreshing the page.
- Check that navigation and forms work.
- Do not leave broken imports, placeholder buttons, or unfinished routes presented as complete.

If the project cannot start or deploy, investigate the actual error logs and fix the root cause before continuing. Do not silently ignore errors.

## 9. Final Verification

Before declaring the milestone complete:
- Confirm the app starts successfully.
- Confirm the database connection works.
- Test creating, editing, and deleting a store.
- Test shopper registration and verification.
- Test questionnaire creation.
- Test creating a task and assigning it to a verified shopper.
- Test form validation and empty states.
- Check responsive layout.
- Report any remaining bugs or incomplete features honestly.

## 10. Final Deliverable

Deliver a runnable, maintainable application with a professional UI, persistent database, and working core Admin workflows.

At the end, provide:
1. Features actually completed.
2. Database tables created.
3. Tests performed and their results.
4. Any incomplete features.
5. Any environment variables or setup steps required.
6. The exact steps to run and preview the application.

Start by inspecting the environment and implementing Stage 1. Continue through the stages as far as the available resources allow. Prioritize a stable, tested application over generating a large amount of untested code.
